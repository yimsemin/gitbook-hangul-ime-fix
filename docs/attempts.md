# 시도 기록

GitBook 편집기에서 한글 IME 입력이 깨지는 문제를 우회하려고 시도한 방법과 결과입니다. 다른 모델이나 세션이 같은 시험을 반복하지 않도록 환경, 시험 방법, 관찰한 사실, 시도별 결과를 적었습니다. 해결된 시도는 아직 없습니다.

## 환경

- Windows 11, Chrome(최신), Microsoft 한글 IME. 사용자는 Tampermonkey를 설치했습니다.
- 시험 대상: GitBook 변경 요청(초안)의 시험용 페이지 "Page 1". 발행·병합하지 않았습니다.
- 사용자 확인 사항: 확장 프로그램 끄기, 맞춤법 검사 끄기, 이전 버전 IME 사용, 다른 브라우저로는 해결되지 않고, 화상 키보드로 입력해도 같습니다.

## 시험 방법

사람의 입력 경로를 재현하려면 실제 IME를 거쳐야 합니다. 확장이 `insertText` 이벤트로 완성된 글자를 넣는 방식은 증상이 나타나지 않아 검증에 쓸 수 없습니다.

- 키 입력 도구: [tools/ime-send-keys.ps1](../tools/ime-send-keys.ps1)이 Windows `keybd_event`로 Chrome 창에 가상 키를 보냅니다. 두벌식 자판 영문 키(`r`=ㄱ, `k`=ㅏ)를 보내면 IME가 `insertCompositionText` 이벤트를 만들어 냅니다.
- 시험 시나리오: 새 줄 끝에서 `rksk ekfk akqk`("가나 다라 마바") 입력 → `{HOME}{RIGHT}{RIGHT}{RIGHT}`로 커서를 3번째 글자 뒤로 이동 → `qk tk `("바 사 ") 입력. 기대 결과는 `가나 바 사 다라 마바`입니다.
- 결과 확인: 확장의 `javascript_tool`로 `[contenteditable=true]`의 `innerText`와 `beforeinput`·`compositionstart`·`compositionend` 이벤트 로그를 읽었습니다.

주의할 점
- 키는 대상 창의 활성 탭으로 갑니다. 시험용 탭이 사용자 창의 백그라운드 탭이면 사용자의 탭에 입력됩니다. 실제로 사용자 페이지에 한 번 입력되어 사고가 있었습니다. 도구는 이제 창 제목이 정확히 1개일 때만 보냅니다. 시험 탭이 활성 탭이어야 하고, 사용자가 같은 창에서 작업하면 안 됩니다. 활성 탭 전환은 `Ctrl+9`(마지막 탭)로 했습니다.
- `keybd_event`에 스캔 코드를 주지 않으면 `KeyboardEvent.code`가 빈 값입니다. 현재 도구는 `MapVirtualKey`로 스캔 코드를 채웁니다. `{HOME}` `{END}`는 `code`가 `Numpad7` `Numpad1`로 보입니다(확장 키 플래그 없음).
- `{HANGUL}`(VK_HANGUL)은 IME 한/영 상태를 전환합니다. 두 번 보내면 원래 상태로 돌아옵니다.
- 시험 페이지는 이전 시험의 글자가 남아 있고, 마지막 시험들로 빈 줄과 깨진 줄이 생겼습니다. 새 시험은 새 페이지에서 시작하는 편이 낫습니다.

## 관찰한 사실

- 줄 끝에서 이어 입력하면 정상입니다. 줄 중간에서 입력하면 새 스페이스 하나가 사라집니다(`가나 바사 다라 마바`).
- 조합이 끝난 뒤 오는 스페이스는 `compositionend` 다음에 `beforeinput(insertText, " ")`로 옵니다. `compositionend` 시점의 DOM 커서는 맞는데, 다음 `beforeinput` 시점에는 한 칸 앞(조합한 글자 앞)으로 돌아가 있는 경우가 있습니다. 편집기가 그 사이에 DOM 커서를 자기 모델 기준으로 되돌리는 것으로 보입니다.
- 한글 조합은 음절마다 `compositionstart`/`compositionend`가 반복됩니다(`바` 끝 → 스페이스 → `사` 시작).
- 코멘트 입력창에서는 조합 중 `Home`을 누르면 마지막 글자가 낱자로 깨지고(`요` → `ㅛ`), 이후 입력이 줄 끝으로 가며 순서가 뒤섞입니다.
- `document.execCommand('insertText'/'delete')`로 글자를 넣고 지우는 방식은 줄 중간에서도 정상입니다. `ㅂ` → 삭제 → `바` → 삭제 → `밧` → 삭제 → `바` → `사` → 공백을 연속 실행해 `가나 |`에 `바사 `가 올바르게 들어갔습니다.
- `beforeinput`의 `insertCompositionText`는 취소할 수 없습니다. 브라우저가 DOM을 먼저 바꿉니다.
- 편집기는 DOM 커서가 아니라 내부 모델의 위치로 글자를 넣는 것으로 보입니다(추정). GitBook 소스는 확인하지 않았습니다.

## 시도별 결과

| # | 방법 | 결과 |
|---|---|---|
| 1 | 조합 직후 DOM 커서를 기록해 두었다가 400ms 동안 `selectionchange`와 `beforeinput`마다 되돌림 | 해결되지 않음. 정상적으로 움직인 커서까지 되돌려 증상이 더 나빠짐 |
| 2 | 위 방식을 조합 직후 첫 `insertText`의 `beforeinput`에서만 1회 적용 | 스페이스가 엉뚱한 위치(`가나 바사다 라 마바`)로 들어감. 편집기가 DOM 커서를 쓰지 않는 것으로 보임 |
| 3 | `window` 캡처 단계에서 조합 이벤트(`compositionstart/update/end`, `insertCompositionText`)를 `stopImmediatePropagation`으로 편집기에 전달하지 않음 | 입력한 글자가 모델에 반영되지 않아 화면에서 사라지고 새 줄도 만들어지지 않음 |
| 4 | 조합 직후 `insertText`를 `preventDefault`로 막고, `requestAnimationFrame`에서 커서를 복구한 뒤 40ms 후 `execCommand('insertText')`로 다시 입력(다음 `compositionstart`에서 즉시 flush) | 해결되지 않음. 줄 끝에서 입력한 첫 줄까지 스페이스 위치가 틀어짐(`가나다바라사 마바`) |
| 5 | OS IME를 영문 상태로 두고 스크립트가 두벌식 조합을 직접 처리(키 `keydown`을 가로채 `execCommand`로 삭제·입력 반복) | 미완. `rk` 한 번은 `가`로 정상 조합됐고 `execCommand`는 true를 반환했습니다. Enter 직후 이어 입력하는 전체 시나리오에서는 조합된 글자가 화면에 나타나지 않았고, 원인을 확인하지 못했습니다. |

시도 1은 [gitbook-hangul-ime-fix.user.js](../gitbook-hangul-ime-fix.user.js)의 이전 버전(0.1.0)이었고, 현재 파일은 시도 5(0.2.0)입니다. 시도 2~4는 파일로 남기지 않았습니다.

## 시도 5의 미해결 지점

- 새 줄(Enter) 직후 이어서 입력하면 `execCommand`가 true를 반환하는데도 글자가 보이지 않습니다. Enter 후 편집기가 블록을 비동기로 다시 만들면서 입력이 사라지는 것으로 추정하지만 확인하지 못했습니다. 입력 사이에 짧은 지연을 두거나 `requestAnimationFrame` 이후에 입력해 보는 것이 첫 확인 대상입니다.
- 줄 중간 시나리오(`{HOME}{RIGHT}×3` 후 입력)는 새 줄 문제 때문에 아직 시험하지 못했습니다. 기존 줄에서 먼저 시험하면 분리할 수 있습니다.
- 이 방식은 사용자가 OS 입력기를 영문으로 두고 단축키로 스크립트의 한글 모드를 켜고 꺼야 합니다. 토글 키와 상태 표시는 아직 없습니다.
- 숨은 입력칸에서 조합을 끝낸 뒤 완성 글자만 넣는 방식(README의 접근 방식 3)은 시험하지 않았습니다. 음절마다 조합이 끊기므로 포커스를 옮기면 조합이 깨질 위험이 있어 보입니다.

## 아직 시도하지 않은 방향

- GitBook 편집기 소스(번들)에서 조합·선택 처리 코드를 찾아 원인을 확정합니다. 편집기가 쓰는 프레임워크를 알면 알려진 우회법이 있는지 찾기 쉽습니다.
- 편집기가 모델에서 읽는 커서를 갱신하는 경로(예: `selectionchange`를 인위적으로 발생시키는 방법)를 찾습니다.
- 편집기가 기대하는 입력 이벤트 순서를 보존하면서 `compositionend` 직후 한 틱 늦춰 스페이스를 처리하는 방법을 정교하게 다듬습니다(시도 4의 변형).
- Git Sync로 연결한 마크다운 파일을 로컬에서 편집하는 우회로입니다. 코멘트 입력은 해결되지 않습니다.
